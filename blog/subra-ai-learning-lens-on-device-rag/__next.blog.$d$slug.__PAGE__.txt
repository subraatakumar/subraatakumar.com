8:T4eb8,<p class="blog-md-p">Learning Lens answers questions about material a user has put in a private Vault. The core engineering problem is to find useful passages from that material and give them to an on-device language model at answer time. We implemented a retrieval-augmented generation (RAG) pipeline: ingest files locally, turn their useful content into searchable text, retrieve matches within the Learning Vault, and pass the matches to an on-device Gemma model.</p>
<p class="blog-md-p">This article describes the implementation in the current Subra AI codebase. It also explains why the design is a practical starting point for a mobile personal Vault, and where its guarantees stop.</p>
<h2 id="first-what-does-rag-mean" class="blog-md-h2">First, what does RAG mean?</h2>
<p class="blog-md-p">Imagine you add a React textbook to the Vault and ask, “How does React decide what to update?” The downloaded language model has general knowledge about React, but it has not memorized your textbook. <strong>Retrieval</strong> finds passages from the textbook that mention the relevant idea. <strong>Augmentation</strong> places those passages beside your question in the model’s input. <strong>Generation</strong> is the model writing an explanation from that input. The three steps make up <em>retrieval-augmented generation</em>, or RAG.</p>
<p class="blog-md-p">This is similar to answering an open-book question: find the useful pages first, then write the answer. The book does not train or change the model. Its passages are supplied only for that answer.</p>
<p class="blog-md-p">For one question, the actual sequence is:</p>
<ol class="blog-md-ol">
<li class="blog-md-li">You import a PDF chapter about React. The app extracts its text and marks it ready for search.</li>
<li class="blog-md-li">You ask how React decides what to update. Search looks for matching words in Learning Vault documents.</li>
<li class="blog-md-li">The app selects a few matching passages and attaches their filenames and any available page markers.</li>
<li class="blog-md-li">Gemma receives the question and passages, then writes an answer. Its instructions ask it to use those passages and cite them.</li>
</ol>
<p class="blog-md-p">The answer is generated when you ask; importing the PDF does not retrain Gemma.</p>

<p class="blog-md-p">Retrieval and generation have distinct jobs. <strong>SQLite</strong> is a database stored on the phone; it selects candidate evidence. <strong>Gemma</strong> is the downloaded language model that reads the evidence and writes an explanation on the phone. The model does not search the database. Keeping the search outside the model lets us filter by Lens before private content enters the prompt.</p>
<h2 id="1-ingest-sources-into-a-local-vault" class="blog-md-h2">1. Ingest sources into a local Vault</h2>
<p class="blog-md-p">Each source is copied into app-owned file storage. A SQLite <code class="blog-md-inline-code">vault_documents</code> record stores its ID, filename, media type, relative file path, Lens ID, processing status, and <strong>derived text</strong>: text extracted from or generated about the original. The original file and derived text have separate lifecycles: a user can delete the original image or recording while keeping its searchable description or transcript.</p>
<p class="blog-md-p">The source types reach searchable text through different paths:</p>

<p class="blog-md-p">The image path is particularly important: merely storing pixels does not make an image retrievable through text search. Before image import, the UI checks for the local model and offers a route to download it if absent. On successful import, the app saves the original image, asks the local vision model to extract readable text and describe meaningful visual content, and stores the result as derived text. If analysis fails, the image remains in the Vault with a <code class="blog-md-inline-code">needs-processing</code> status rather than being marked searchable.</p>
<p class="blog-md-p">Audio likewise becomes searchable only after transcription. The app stores chunk checkpoints and combines completed transcripts with time markers. The original media is still available independently of the transcript.</p>
<p class="blog-md-p">This design suits a private mobile Vault: <strong>ingestion</strong> is the one-time preparation that turns an imported file into text the app can search. Chat then searches that text. It also gives the app a clear readiness state for each document: saved is different from <strong>indexed</strong>, which means prepared for search.</p>
<h2 id="2-restrict-retrieval-to-the-learning-lens" class="blog-md-h2">2. Restrict retrieval to the Learning Lens</h2>
<p class="blog-md-p">Vault records carry a <code class="blog-md-inline-code">lens_id</code>, such as <code class="blog-md-inline-code">learning</code>. Learning Chat passes that ID into retrieval, and the database query searches only rows with the same ID. This is what <strong>Lens scope</strong> means here: a question in Learning Lens searches Learning Vault content.</p>
<p class="blog-md-p">The database applies this filter before passing results to Gemma. Content from another Lens should not be supplied to the model in the first place. The same shared Vault and Chat components can serve future Lenses with different scopes and grounding modes.</p>
<h2 id="3-search-locally-with-fts5-then-select-chunks" class="blog-md-h2">3. Search locally with FTS5, then select chunks</h2>
<p class="blog-md-p"><strong>FTS5</strong> means <strong>Full-Text Search 5</strong>. It is SQLite’s text-search extension. It builds a separate search index that helps the app find words inside long documents quickly. If you ask about “reconciliation,” the app can find candidate documents containing that term without reading every textbook in JavaScript. The index stores derived text, not the original PDF, image, or audio bytes.</p>
<p class="blog-md-p">The search table stores <code class="blog-md-inline-code">lens_id</code> alongside the filename and content:</p>

      <div class="blog-code-wrap">
        <div class="blog-code-head">
          <span class="blog-code-lang">SQL</span>
          <button data-copy class="blog-copy-btn">Copy</button>
        </div>
        <pre class="blog-md-pre"><code class="language-sql">CREATE VIRTUAL TABLE IF NOT EXISTS vault_search
USING fts5(
  document_id UNINDEXED,
  lens_id UNINDEXED,
  name,
  content
);
</code></pre>
      </div>
    
<p class="blog-md-p">The retrieval query uses both the Lens filter and an FTS match:</p>

      <div class="blog-code-wrap">
        <div class="blog-code-head">
          <span class="blog-code-lang">SQL</span>
          <button data-copy class="blog-copy-btn">Copy</button>
        </div>
        <pre class="blog-md-pre"><code class="language-sql">SELECT name, content
FROM vault_search
WHERE lens_id = ? AND vault_search MATCH ?
LIMIT ?;
</code></pre>
      </div>
    
<p class="blog-md-p">Each <code class="blog-md-inline-code">?</code> is a parameter supplied by the app: the Lens ID, the search expression, and the maximum candidate count. <code class="blog-md-inline-code">UNINDEXED</code> means FTS5 stores that field for identification and filtering without adding its words to the full-text index. <code class="blog-md-inline-code">MATCH</code> asks FTS5 to look for query terms in the indexed text.</p>
<p class="blog-md-p">A normal database query can find an exact value such as a document ID. FTS5 is optimized for finding terms within longer text. It narrows the search to candidate documents before JavaScript scores smaller passages.</p>
<p class="blog-md-p">The first version of retrieval scanned indexed documents and counted query-term matches. We added FTS5 as a local candidate search. The app rebuilds its search rows from indexed Vault documents during database initialization and updates a row when imported or derived content changes. Deleting an entry and its inference also removes its search row. The search index is derived from the Vault records; it is not another copy of the original media files.</p>
<p class="blog-md-p">If FTS5 is unavailable, retrieval falls back to the earlier keyword scan. This fallback keeps local search functional across SQLite builds with different extension support.</p>
<p class="blog-md-p">The current index is <strong>document-level</strong>: one FTS5 row represents a document’s searchable text. A <strong>chunk</strong> is a shorter piece of that text. After FTS5 finds candidate documents, the app splits their content into chunks of up to roughly 220 words each, scores each chunk by the number of matching query terms, discards zero-match chunks, sorts the rest, and returns at most four. These are word counts, not model tokens. This second filter is necessary: a document match does not mean every part of that document is relevant. A 100-page PDF may mention React on many pages, while only one paragraph addresses the question.</p>
<p class="blog-md-p">The question is split into terms longer than two characters. The FTS5 query looks for any of those terms; chunk scoring then favors passages containing more of them. This is a straightforward word-match strategy. It does not measure whether two differently worded sentences mean the same thing. The current chunk score checks whether each term appears in the chunk, not how often it appears.</p>
<p class="blog-md-p">In simplified form:</p>

      <div class="blog-code-wrap">
        <div class="blog-code-head">
          <span class="blog-code-lang">TS</span>
          <button data-copy class="blog-copy-btn">Copy</button>
        </div>
        <pre class="blog-md-pre"><code class="language-ts">const candidates = await searchIndexedDocuments(question, lensId);
const context = candidates
  .flatMap(document => splitIntoChunks(document.content))
  .map(chunk => ({chunk, score: countMatchingTerms(chunk, question)}))
  .filter(result => result.score > 0)
  .sort((a, b) => b.score - a.score)
  .slice(0, 4);
</code></pre>
      </div>
    
<p class="blog-md-p">This is a good first mobile implementation because SQLite is already used for Vault metadata, search stays on the device, and keyword matches are easy to inspect. It is <strong>not</strong> semantic retrieval: a question that paraphrases a passage without sharing its vocabulary can be missed. Document-level FTS can also overlook a useful late passage if the candidate limit is filled by other documents.</p>

<p class="blog-md-p">The <strong>prompt</strong> is the text the app sends to Gemma for one answer. The retriever formats selected content with a source label and adds it to that prompt. For a PDF page, the intended shape is:</p>

<p class="blog-md-p">The Chat controller also includes the latest question, conversation context, and Lens-specific instructions. Learning Lens is configured with <code class="blog-md-inline-code">groundingMode: 'vault'</code>. Its system instruction tells Gemma to use only the supplied Vault sources, cite their bracketed labels, and say that the Learning Vault lacks enough information if the sources are insufficient.</p>
<p class="blog-md-p">The generated answer is produced locally through the same on-device model service used for chat. The model must be downloaded before generation or media inference can run. The Vault can still store and list files without a model, but RAG answering depends on that model being available.</p>
<p class="blog-md-p">The practical benefit of this design is a small, controlled prompt: the model receives a few selected passages instead of entire textbooks or recordings. This reduces <strong>context use</strong>, the amount of input the model must hold while answering, and gives it identifiable source labels to refer to.</p>
<h2 id="what-this-implementation-does-and-does-not-guarantee" class="blog-md-h2">What this implementation does and does not guarantee</h2>
<p class="blog-md-p">The application enforces <strong>Lens-scoped retrieval</strong> in SQL. It also prevents unprocessed documents from entering the search index by indexing only records marked <code class="blog-md-inline-code">indexed</code>. The Learning prompt requests Vault-only, cited answers.</p>
<p class="blog-md-p">There are still limits to the current implementation:</p>
<ul class="blog-md-ul">
<li class="blog-md-li"><strong>Vault-only answers are instructed, not mechanically verified.</strong> The controller sends a no-match notice to the model, but it does not yet stop generation when retrieval returns no evidence. A model can still answer from prior knowledge despite the instruction. Automatically returning “I couldn’t find enough in your Vault” before model generation would be <strong>application-level abstention</strong>.</li>
<li class="blog-md-li"><strong>Citations are requested, not checked.</strong> The model writes citation text; the app does not verify each claim against a retrieved chunk. Page markers are embedded in document content and chunking may separate a later chunk from its page marker, so page attribution is not always reliable. Audio timestamps remain text within the retrieved passage rather than structured citation metadata.</li>
<li class="blog-md-li"><strong>Image descriptions may be wrong.</strong> The local vision model creates a useful searchable representation, but that representation is model output rather than exact OCR with confidence scores.</li>
<li class="blog-md-li"><strong>Retrieval is lexical, meaning it matches words.</strong> FTS5 and term counting are fast and transparent, but synonyms and conceptual questions can fail when wording differs. <strong>Semantic retrieval</strong> would compare meaning, often by turning text into numeric vectors called embeddings.</li>
<li class="blog-md-li"><strong>Follow-up retrieval uses the latest question.</strong> Earlier conversation is included in the generation prompt, but the search query is built from the latest user message. A follow-up such as “explain that further” may retrieve no useful passage because it does not repeat the subject’s terms.</li>
</ul>
<p class="blog-md-p">These limits matter because “RAG” does not automatically mean “verified answer.” The current system grounds the prompt in retrieved local content; a stronger guarantee requires application-level abstention and citation validation.</p>
<h2 id="why-this-was-the-right-starting-architecture" class="blog-md-h2">Why this was the right starting architecture</h2>
<p class="blog-md-p">For a personal learning Vault on a phone, FTS5 gives us a valuable combination: local operation, no external search service, modest implementation complexity, clear Lens filtering, and inspectable matches. It also reuses the app’s SQLite storage. A separate <strong>vector index</strong> would store embeddings for meaning-based search and require additional on-device computation and storage. FTS5 is a strong starting choice for exact words, names, and technical terms; it is not universally the best retriever for every question.</p>
<p class="blog-md-p">The implementation separates concerns cleanly:</p>
<ol class="blog-md-ol">
<li class="blog-md-li">Ingestion converts each media type into searchable text.</li>
<li class="blog-md-li">SQLite stores and scopes that text.</li>
<li class="blog-md-li">Retrieval selects a bounded amount of evidence.</li>
<li class="blog-md-li">The local model explains the evidence.</li>
</ol>
<p class="blog-md-p">That split lets us improve retrieval without rebuilding the Chat UI or changing the privacy model.</p>
<h2 id="the-next-rag-improvements" class="blog-md-h2">The next RAG improvements</h2>
<p class="blog-md-p">The next step is a first-class <code class="blog-md-inline-code">vault_chunks</code> table with <code class="blog-md-inline-code">document_id</code>, <code class="blog-md-inline-code">lens_id</code>, text, page number or audio time range, and processing version. FTS5 should index those chunks directly. This would avoid splitting full documents on every query and keep page or time information attached to each result.</p>
<p class="blog-md-p">Then we can add three safeguards in order:</p>
<ol class="blog-md-ol">
<li class="blog-md-li"><strong>Application-level abstention:</strong> if retrieval finds no sufficiently relevant chunk, return a Vault-insufficient response before calling Gemma.</li>
<li class="blog-md-li"><strong>Citation validation:</strong> attach retrieved chunk IDs to answers and check that displayed citations refer to supplied evidence.</li>
<li class="blog-md-li"><strong>Hybrid retrieval where needed:</strong> combine FTS5 word matches with local embedding matches for paraphrased questions, then rank the combined results and keep a small context set.</li>
</ol>
<p class="blog-md-p">The best retrieval method depends on corpus size and question style. Exact technical terms in a small collection often work well with FTS5. A large textbook library or questions expressed in different wording can justify chunk-level indexing and local semantic search. We can make that choice using a test set of questions with expected documents, pages, timestamps, and unanswerable cases.</p>
<h2 id="closing" class="blog-md-h2">Closing</h2>
<p class="blog-md-p">Subra AI’s Learning Lens RAG pipeline runs extraction, search, and generation on the device. Its current strength is the clear boundary between a Lens-scoped Vault, local evidence retrieval, and local answer generation. Its current weakness is that relevance and citations are still partly delegated to the model. The architecture makes those limits visible and gives us a direct path to stronger retrieval and verifiable grounding as the Learning Vault grows.</p>

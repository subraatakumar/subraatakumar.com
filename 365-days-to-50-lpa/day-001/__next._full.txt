<h2>Step 3: Capture our first explanation</h2>
<p>Our exercise connects something familiar—a name displayed on a screen—to a backend concern: data may have a different shape from what our interface expects.</p>

<h2>Step 4: Work through the failure</h2>
<p>The first call prints:</p>
<pre><code class="language-text">Hello, ASHA
</code></pre>
<p>The second call throws a <code>TypeError</code>. Its exact wording depends on the runtime, but the reason is that <code>null</code> has no <code>toUpperCase</code> method.</p>
<p>This is a useful failure. The function assumes <code>name</code> is a string without checking that assumption. In a real product, a similar problem might come from an API response, stored data, or an AI-generated answer.</p>
<p>TypeScript helps us reason about code through types, but a type declaration alone does not inspect incoming network data while the program runs. We will study that boundary more deeply when we build our backend services. Today we can make it visible with a small JavaScript check.</p>
<h3>Define the behaviour before changing the code</h3>
<p>We choose a simple contract for this exercise:</p>
<ul>
<li>A non-empty string name produces an uppercase greeting.</li>
<li>Spaces around a valid name are removed.</li>
<li>Missing, empty, or non-string names produce <code>Hello, friend</code>.</li>
</ul>
<p>A <strong>contract</strong> describes the behaviour callers can expect. Another product might reject invalid input instead. Our decision today is to display a friendly fallback, and our journal records why.</p>
<p>We ask the review assistant:</p>
<pre><code class="language-text">Act as our review assistant for this small JavaScript exercise.

Do not claim that tests passed unless we provide execution results.
We will decide what to accept and run the checks ourselves.
</code></pre>
<p>We keep its suggestions separate from our original answer. If it introduces a library or rewrites the whole example, we ask how that helps this specific contract.</p>
<h2>Step 5: Make and verify one correction</h2>
<p>Here is a worked correction we can compare with the assistant’s proposal:</p>
<pre><code class="language-js">function greeting(user) {
  if (user === null || typeof user !== "object") {
    return "Hello, friend";
  }

  if (typeof user.name !== "string") {
    return "Hello, friend";
  }

  const name = user.name.trim();

  if (name.length === 0) {
    return "Hello, friend";
  }

  return "Hello, " + name.toUpperCase();
}
</code></pre>
<p>The first condition checks whether a usable object was provided. We check <code>null</code> explicitly because JavaScript reports <code>typeof null</code> as <code>"object"</code>.</p>
<p>The second condition checks the property we need. An object can exist while its <code>name</code> is missing, a number, or <code>null</code>.</p>
<p>Only after confirming that <code>name</code> is a string do we call <code>trim()</code>. This removes surrounding whitespace. We then handle an empty result before constructing the greeting.</p>
<p>We replace the original function and calls in <code>baseline.js</code> with the corrected function, followed by these checks:</p>
<pre><code class="language-js">const cases = [
  [{ name: "Asha" }, "Hello, ASHA"],
  [{ name: "  Asha  " }, "Hello, ASHA"],
  [{ name: "   " }, "Hello, friend"],
  [{ name: null }, "Hello, friend"],
  [{ name: 42 }, "Hello, friend"],
  [{}, "Hello, friend"],
  [null, "Hello, friend"],
  [undefined, "Hello, friend"],
];

for (const [input, expected] of cases) {
  const actual = greeting(input);

  if (actual !== expected) {
    throw new Error("Expected: " + expected + "; received: " + actual);
  }
}

console.log("Passed " + cases.length + " checks.");
</code></pre>
<p>Each entry pairs an input with its expected output. The loop calls our function and compares the result. A mismatch throws an error; reaching the final line means all listed comparisons succeeded.</p>
<p>The expected output for this worked example is:</p>
<pre><code class="language-text">Passed 8 checks.
</code></pre>
<p>We record what our own run actually prints. These checks cover the contract we chose for a small exercise; they do not prove that we have built a complete API validation system.</p>
<p>To check our understanding, we explain why <code>trim()</code> comes after the type check. We also add one case of our own and predict the result before running it.</p>

</code></pre>
<h2>Step 7: Record tools, decisions, and visibility</h2>
<p>Our journal should name the editor, runtime, assistant, and model we actually used. If the model name is not visible, we write “not shown.” We also record whether the assistant only saw pasted text or could act inside our workspace.</p>
<p>For each material choice, we record the option selected, why it fits today, an alternative we deferred, how we checked it, and what would make us reconsider. For example:</p>
<pre><code class="language-text">Decision: Use the existing chat assistant for Day 1.
Reason: It can review this small snippet with no additional setup.
Deferred alternative: A local coding agent, to evaluate during Week 2.
Limitation: We copy suggestions and execution output manually.
Verification: We ran the accepted code locally and inspected the result.
Revisit: When workspace editing or repeatable local-model use becomes useful.
</code></pre>
<p>We also inventory our GitHub, Notion, and public profile status. GitHub will hold versioned work; Notion can provide a readable dashboard; the website and LinkedIn can help others discover our evidence. Today, recording existing links and preparing one draft is enough. Account setup and automation have their own scheduled sessions.</p>
<p>We can ask a documentation assistant to prepare a short update from the journal:</p>
<pre><code class="language-text">Using only the completed work in this journal, draft a short Day 1 update.
Include what we attempted, what failed, what we changed, what we verified,
and our next question. Preserve uncertainty. Do not invent scores,
screenshots, repository links, or successful checks. Leave it as a draft.
</code></pre>
<p>Before sharing, we check that each claim matches our results and that the draft contains only material we intend to make public. Our example uses fictional names and standalone code, so there is no reason to include employer code or account credentials.</p>
<p>If Git is already configured, we may commit the two files through our normal workflow after reviewing them. Otherwise, saving them locally completes today’s storage requirement. Git records changes and author-supplied timestamps; it does not independently certify when or by whom a task was completed.</p>
<h2>Our stopping point</h2>
<p>At 90 minutes, we save our files and mark the session accurately. A useful Day 1 result contains:</p>
<ul>
<li>A workspace and journal naming the tools we used.</li>
<li>Our original prediction and actual exercise output.</li>
<li>A reviewed correction with the checks we ran, or a specific unresolved blocker.</li>
<li>One explanation in our own words and one gap to revisit.</li>
<li>A decision entry and a public-update draft labelled with its actual status.</li>
</ul>
<p>If something failed, we record the error and the next diagnostic step. That makes the session useful without claiming that unfinished work succeeded.</p>
<h2>Questions we may have</h2>
<h3>Do we need to install every AI tool today?</h3>
<p>We need one usable assistant. We record other tools as existing, deferred, or not configured, then evaluate them in their scheduled sessions.</p>
<h3>What if JavaScript is new to us?</h3>
<p>We can follow the worked example, record unfamiliar terms, and finish with a guided result. We may need additional foundation sessions before following the experienced-engineer pace.</p>
<h3>Does passing these checks mean we know backend engineering?</h3>
<p>It demonstrates one small input-handling exercise. Broader capability requires more varied implementation, debugging, design, and operational evidence across the journey.</p>

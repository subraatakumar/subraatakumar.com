What we will do today

We begin our transition toward Senior/Staff Mobile Engineering with full-stack and applied-AI capabilities by creating a place to work, choosing one available AI assistant, and completing one small exercise. By the end of this chapter, we will have a local folder, a JavaScript file we have run, and a journal explaining our decisions and starting knowledge.

This chapter is a plan we can follow. Its sample answers and results are illustrative; our actual results belong in our own journal after we perform the exercise.

We already bring different strengths to the journey. Some of us have delivered React Native applications for years. Others are still learning JavaScript. Today’s exercise gives us a small starting measurement we can revisit. It does not assess our entire engineering ability or determine our readiness for a job title.

Our workspace and assistant

A workspace is simply a folder containing the files for our work. We can open it in a code editor and keep the exercise beside the explanation of why we wrote it.

An AI assistant receives our instructions and produces suggestions. A coding agent may also have tools that read files, edit code, or execute commands. We will start with an assistant we already have access to. A browser chat is sufficient for today: we can copy a short snippet into it and apply reviewed suggestions ourselves.

We will use that assistant in two clearly separated roles:

  • Planning assistant: helps us create a short checklist and understand unfamiliar steps.
  • Review assistant: challenges our explanation and suggests tests after our first attempt.

These are two scoped conversations or tasks. We do not need two products or a custom multi-agent system. We will build and understand more capable agents later in the journey.

If a coding agent is already installed, we use its review or approval controls and limit it to this new folder. For today, it needs no access to our employer’s repositories, cloud accounts, or public profiles.

What happens to Ollama, Hermes, and the coding CLI?

We record their current status today and use one available assistant during Week 1. In Week 2, we select our primary coding workflow and benchmark one local model with Ollama if our hardware supports it. In Week 3, we apply that workflow to our first mobile screen. In Week 4, we prepare evidence drafts with Hermes or our existing assistant; manual publication remains sufficient. This follows the complete schedule.

If a tool is already available, we record what we actually use. If it is absent, we write “not configured.” We do not need to install all the candidates before beginning.

The 90-minute session

Reading and troubleshooting belong inside the time budget. We stop when the session ends and record anything unfinished.

Step 2: Check how we will run JavaScript

JavaScript needs a runtime: a program that executes JavaScript instructions. A browser includes one. Node.js also runs JavaScript, including from files outside a browser.

If a terminal is already available in our editor, we enter:

node --version

This asks Node.js to print its installed version. We copy the actual output into the journal. If the command is unavailable, we record that and use the browser route below. We do not spend the session troubleshooting installation.

With Node.js available, we open the terminal in the day-001 folder. After saving code in baseline.js, we can run it with:

node baseline.js

If we get a “cannot find module” or file-not-found message, we check that the terminal is in day-001 and that the filename is exactly baseline.js.

Browser route

We open a blank browser tab, open its developer tools, and select the Console panel. The console can evaluate JavaScript we type. We enter the small examples from this chapter there and keep the same code in our local file for reference. If the browser restricts pasting, we type the short example ourselves.

When repeating declarations causes an “already declared” error, a fresh blank tab gives us a fresh console. Our journal records that we used a browser rather than Node.js.

Step 3: Capture our first explanation

Our exercise connects something familiar—a name displayed on a screen—to a backend concern: data may have a different shape from what our interface expects.

An API is an interface through which software exchanges requests and responses. A mobile application often receives an object from an API and turns its fields into visible text.

We start with this function:

function greeting(user) {
  return "Hello, " + user.name.toUpperCase();
}

console.log(greeting({ name: "Asha" }));
console.log(greeting({ name: null }));

greeting accepts an object named user. It reads the name property and calls toUpperCase(), a method that converts a string to uppercase. console.log() prints a result.

Before running the code, we write two predictions in our journal:

  1. What will the first call print?
  2. What will happen when name is null, meaning that no value is present?

We then run the code and preserve our actual output. We write a short explanation before consulting the assistant. If we do not know the answer, “I do not yet understand this behaviour” is useful evidence.

Checkpoint: we save our prediction and first output before reading the worked explanation below. Reading the explanation first is fine for learning; we simply label that attempt “guided” in our journal.

Step 4: Work through the failure

The first call prints:

Hello, ASHA

The second call throws a TypeError. Its exact wording depends on the runtime, but the reason is that null has no toUpperCase method.

This is a useful failure. The function assumes name is a string without checking that assumption. In a real product, a similar problem might come from an API response, stored data, or an AI-generated answer.

TypeScript helps us reason about code through types, but a type declaration alone does not inspect incoming network data while the program runs. We will study that boundary more deeply when we build our backend services. Today we can make it visible with a small JavaScript check.

Define the behaviour before changing the code

We choose a simple contract for this exercise:

  • A non-empty string name produces an uppercase greeting.
  • Spaces around a valid name are removed.
  • Missing, empty, or non-string names produce Hello, friend.

A contract describes the behaviour callers can expect. Another product might reject invalid input instead. Our decision today is to display a friendly fallback, and our journal records why.

We ask the review assistant:

Act as our review assistant for this small JavaScript exercise.
We will provide the code, our original explanation, and actual output.

First, ask one question that checks our understanding of the failure.
Then suggest the smallest change meeting this contract:
- Trim and uppercase a non-empty string name.
- Return "Hello, friend" for missing, empty, or non-string names.

Explain each condition and suggest three edge cases.
Do not claim that tests passed unless we provide execution results.
We will decide what to accept and run the checks ourselves.

We keep its suggestions separate from our original answer. If it introduces a library or rewrites the whole example, we ask how that helps this specific contract.

Step 5: Make and verify one correction

Here is a worked correction we can compare with the assistant’s proposal:

function greeting(user) {
  if (user === null || typeof user !== "object") {
    return "Hello, friend";
  }

  if (typeof user.name !== "string") {
    return "Hello, friend";
  }

  const name = user.name.trim();

  if (name.length === 0) {
    return "Hello, friend";
  }

  return "Hello, " + name.toUpperCase();
}

The first condition checks whether a usable object was provided. We check null explicitly because JavaScript reports typeof null as "object".

The second condition checks the property we need. An object can exist while its name is missing, a number, or null.

Only after confirming that name is a string do we call trim(). This removes surrounding whitespace. We then handle an empty result before constructing the greeting.

We replace the original function and calls in baseline.js with the corrected function, followed by these checks:

const cases = [
  [{ name: "Asha" }, "Hello, ASHA"],
  [{ name: "  Asha  " }, "Hello, ASHA"],
  [{ name: "   " }, "Hello, friend"],
  [{ name: null }, "Hello, friend"],
  [{ name: 42 }, "Hello, friend"],
  [{}, "Hello, friend"],
  [null, "Hello, friend"],
  [undefined, "Hello, friend"],
];

for (const [input, expected] of cases) {
  const actual = greeting(input);

  if (actual !== expected) {
    throw new Error("Expected: " + expected + "; received: " + actual);
  }
}

console.log("Passed " + cases.length + " checks.");

Each entry pairs an input with its expected output. The loop calls our function and compares the result. A mismatch throws an error; reaching the final line means all listed comparisons succeeded.

The expected output for this worked example is:

Passed 8 checks.

We record what our own run actually prints. These checks cover the contract we chose for a small exercise; they do not prove that we have built a complete API validation system.

To check our understanding, we explain why trim() comes after the type check. We also add one case of our own and predict the result before running it.

Step 6: Record capability and assistance separately

We avoid giving ourselves a single score for “backend engineering” based on this function. Instead, we record what this particular exercise demonstrated.

Dimension What we record
Understanding Can we explain the failure and each condition?
Verification Which cases did we actually run, and what happened?
Debugging Can we investigate a failed case and explain a correction?
Assistance Which suggestions or worked examples did we use?
Remaining gap What do we still need help understanding?

Using AI or documentation does not reduce demonstrated capability by itself. What matters is whether we can judge the suggestion, verify it, and take responsibility for the result. Following a worked example is a valid first step; we record it accurately so later comparisons remain useful.

Here is an illustrative journal excerpt, not a claim about our own session:

Original prediction: I expected the second call to print "Hello, NULL".
Observed: It threw a TypeError.
Review feedback: The assistant asked whether null is a string.
Accepted change: Check the input and name before calling string methods.
Rejected change: Adding a validation package for this tiny exercise.
Verification: Ran the eight supplied cases and one new missing-name case.
Understanding: I can explain why the string check precedes trim().
Gap: I want to understand how runtime validation fits with TypeScript types.

Step 7: Record tools, decisions, and visibility

Our journal should name the editor, runtime, assistant, and model we actually used. If the model name is not visible, we write “not shown.” We also record whether the assistant only saw pasted text or could act inside our workspace.

For each material choice, we record the option selected, why it fits today, an alternative we deferred, how we checked it, and what would make us reconsider. For example:

Decision: Use the existing chat assistant for Day 1.
Reason: It can review this small snippet with no additional setup.
Deferred alternative: A local coding agent, to evaluate during Week 2.
Limitation: We copy suggestions and execution output manually.
Verification: We ran the accepted code locally and inspected the result.
Revisit: When workspace editing or repeatable local-model use becomes useful.

We also inventory our GitHub, Notion, and public profile status. GitHub will hold versioned work; Notion can provide a readable dashboard; the website and LinkedIn can help others discover our evidence. Today, recording existing links and preparing one draft is enough. Account setup and automation have their own scheduled sessions.

We can ask a documentation assistant to prepare a short update from the journal:

Using only the completed work in this journal, draft a short Day 1 update.
Include what we attempted, what failed, what we changed, what we verified,
and our next question. Preserve uncertainty. Do not invent scores,
screenshots, repository links, or successful checks. Leave it as a draft.

Before sharing, we check that each claim matches our results and that the draft contains only material we intend to make public. Our example uses fictional names and standalone code, so there is no reason to include employer code or account credentials.

If Git is already configured, we may commit the two files through our normal workflow after reviewing them. Otherwise, saving them locally completes today’s storage requirement. Git records changes and author-supplied timestamps; it does not independently certify when or by whom a task was completed.

Our stopping point

At 90 minutes, we save our files and mark the session accurately. A useful Day 1 result contains:

  • A workspace and journal naming the tools we used.
  • Our original prediction and actual exercise output.
  • A reviewed correction with the checks we ran, or a specific unresolved blocker.
  • One explanation in our own words and one gap to revisit.
  • A decision entry and a public-update draft labelled with its actual status.

If something failed, we record the error and the next diagnostic step. That makes the session useful without claiming that unfinished work succeeded.

Questions we may have

Do we need to install every AI tool today?

We need one usable assistant. We record other tools as existing, deferred, or not configured, then evaluate them in their scheduled sessions.

What if JavaScript is new to us?

We can follow the worked example, record unfamiliar terms, and finish with a guided result. We may need additional foundation sessions before following the experienced-engineer pace.

Does passing these checks mean we know backend engineering?

It demonstrates one small input-handling exercise. Broader capability requires more varied implementation, debugging, design, and operational evidence across the journey.

What comes next?

In Day 2, we connect our starting experience and gaps to a target-role scorecard. We now have a concrete example of the daily process we will repeat: define behaviour, use assistance, inspect the result, verify it, and record the reasoning.
